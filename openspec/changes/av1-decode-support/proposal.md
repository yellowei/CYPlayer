# Proposal — av1-decode-support

## Why

用户遇到「库里没有该解码器」的媒体文件时只看到黑屏，具体报错信息不知道。现场核实：错误其实早已被检测到——「找不到解码器」的错误码与人话文案目录都存在多年，只是没接到可见出口（内部知道、外部沉默）。同时上游 CYFFmpeg 仓将按 FFmpeg 4.4 LTS 重编（原生 av1dec 自 4.3 起可用），消费侧零代码迁移是这条链的核心卖点——它需要一次真编译加一次真跑来钉死，这正落在本变更职责内。

## What Changes

- 新增面向消费者的上报行为：当播放启动因「流的编码器在升级后的库里没有可用解码器」而失败时，把早已存在的错误码经现有文案目录填成报错内容，通过新增的可选上报回调投递给已登记消费者（规则型变更，最小拦截条件/放行例外/等价路径/挂载点见 Rule Boundary）。
- 新增验证契约：上游重建产物落地后，整工作区真编译一次＋真跑**具名真 AV1 样片**一次（来源与批准记录见 clarify User Answers 2026-11-20 条；根目录样本降为补充对照），钉死「零代码迁移」（解码 API 调用点一处不改）与「AV1 原生软解路由生效」（渲染通路锚点有帧抵达）。
- 测试落点 TestVideoTests target：既有 stub 方法（testExample/testPerformanceExample）原样保留，新增断言方法/文件。
- 无 BREAKING：既有 delegate 实现者、既有脚手架测试、既有错误码枚举均不动。

## 契约变更点

本仓无 DDL、无 HTTP 端点；接口契约仅库公开面，逐条列明：

| # | 类型 | 内容 | 兼容性影响 |
|---|---|---|---|
| 1 | 接口契约（新增） | FFmpeg 管线面向消费者的协议上新增**一个**可选上报回调，建议签名 `- (void)CYFFmpegPlayer:(CYFFmpegPlayer *)player didFailPlaybackWithError:(NSError *)error;`（名称与「启动失败」脱钩、对齐采纳 (b) 后的全原因口径，第 2 轮审查 Low②；命名实施时对齐仓内既有前缀风格，签名语义不变） | 向后兼容追加：@optional 实现，既有 conformer 零影响 |
| 2 | 错误码（不新增） | 复用既有错误码目录（含 cyPlayerErrorCodecNotFound）；本变更使其首次从可见出口可达，投递内容即该目录现成人话文案 | 枚举成员不变，无破坏 |
| 3 | 公开属性语义澄清 | 公共包装类的可观察 error 属性（文档承诺 support observe）服务 AVFoundation 路线，语义不变；FFmpeg 管线当前无此公开出口，缺口由第 1 条回调补 | 仅行为增量，无破坏 |

## Implementation Outline（实施逻辑）

1. 数据来源：播放器打开媒体文件，解码模块辨认每条流的编码器，在升级后的解码库里查找可用解码器。
2. 判定落点：某条流的编码器在库里没有可用解码器时（损坏文件、编码标签与实际流不符的仍会命中——真 VP9 流升级前后都有可用解码器，属放行侧例子；现代编码升级后不再命中——那正是验证能力要证的），这个原因与其他失败原因（打开文件失败、音频解码失败等）一起汇入同一个业务动作——「播放失败落定」（该汇聚动作同时接收运行期与切换期的失败路径，逐条判定见 Rule Boundary）。
3. 投递：在该业务动作上，把失败原因填入内部沿用多年的人话文案目录，组成报错内容，经新增的可选上报回调投递给已登记的消费者；未实现该回调的消费者不受影响，既有状态通知语义照旧。
4. 划入链路 A（上报接线）适配：即步骤 1-3；最小拦截条件、放行例外、等价执行路径逐条结论见下方 Rule Boundary 表。
5. 划入链路 B（真编译＋真跑）适配：上游产物落地后整工作区编译一次（解码 API 调用点零迁移，断言其与现状清单逐字一致），再按既有测试工程运行约定在运行环境真跑一次**具名真 AV1 样片**（入库副本，见 clarify User Answers 2026-11-20 条），断言帧抵达渲染通路锚点；根目录样本按甄别结果定夺作补充对照，先完成精确编码甄别再定补充断言对象。
6. 下游 CYFileBrowser 的端到端钉归其自身 change（划界排除，不在本仓排任务）。

## Rule Boundary（规则边界）

本变更为规则型（新增可见上报行为），四要素承 clarify 规则边界基线：

| 规则 | 该拦的条件 | 该放的例外与合法反例（附应有处理） | 判定挂载点 |
|---|---|---|---|
| 解码失败上报（播放失败落定） | 流的编码器在升级后的库里没有可用解码器（最小条件：单条流判定失败即成立，例如损坏文件/编码标签与实际流不符） | 升级后可解码的流（含现代编码）正常播放、不上报——合法反例：现代编码样片升级后应正常出画面（验证能力所钉），处理：正常播放、不上报 | 挂在「播放失败落定」这一业务动作上（所有失败原因共同经过的汇聚动作），不挂底层共享函数；该动作天然接收下方全部路径（第 1 轮审查采纳方案 (b)，2026-11-20） |

同一业务意图的其它执行路径（共用同一上报机制的路径，含复用同一汇聚动作的运行期与切换期喂入者，逐条结论）：

- 音频解码失败路径（含音频管线运行期判定点命中）→ 经同一挂载点照常上报，内容与音频侧触发原因一致，判定正确触发 ✅。
- 解封装/打开文件失败路径 → 经同一挂载点照常上报，内容对应该环节错误码文案，判定正确触发 ✅。
- 运行期缓冲超时路径 → 经同一挂载点照常上报，内容对应其触发原因，判定正确触发 ✅（挂载点即汇聚动作本身，天然覆盖运行期；论证见 design Rule Boundary Attachment）。
- 运行期 EOF/缓冲监视边缘失败路径 → 经同一挂载点照常上报，判定正确触发 ✅。
- 切流/切清晰度失败路径 → 经同一挂载点照常上报，判定正确触发 ✅（失败侧原本沉默，判定以不沉默原则为据；成功侧既有显式反馈仅切清晰度为活代码——切流的在约 `:398` 系注释态）。
- 其余既有错误码路径（流信息未找到/流未找到等）→ 同理经同一挂载点统一抵达，内容与触发原因一一对应，判定正确触发 ✅。

三面场景（拦截/放行/等价路径）见 specs/decode-failure-reporting；挂载点为何不被复用底层动作的其它流程误触，见 design Rule Boundary Attachment。

## Capabilities

### New Capabilities

- `decode-failure-reporting`: 无可用解码器时必须抵达可见出口——错误码早已存在，接线是增量；规则型契约（最小拦截条件/放行例外/等价路径/挂载点齐备）。
- `av1-playback-verification`: 上游重建产物落地后真编译＋真跑各一次，钉死「零代码迁移」与「AV1 原生软解路由生效」。

### Modified Capabilities

无（本仓主 spec 目前为空集，两能力均为新建）。
